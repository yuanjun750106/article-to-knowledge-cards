# make-knowledge-cards

一个把长文章变成知识卡片的 Skill：输入一段粘贴的文本或一个本地 Markdown / TXT 文件，输出一组
可以反复复习的卡片（目标 5~8 张，原文知识点确实不够时给 3~4 张并说明原因），每张卡片包含标题、
核心知识、简明解释，以及一个例子或自测问题。

## 一、解决什么问题

读完一篇长文并不等于记住了它。常见的两种做法都不够好：

- **只做摘要**：摘要按原文顺序复述内容，篇幅还是太长，不能用来自测，过几天依然要重读原文。
- **直接让模型"提炼要点"**：模型很愿意补充原文没写的背景、数据和"最佳实践"，产出看起来更完整，
  实际上混入了无法核对的二手信息；也常常把一个知识点拆成两条来凑数量，或者把原文的一整段
  搬进卡片里。

这个 Skill 把目标定得更窄也更硬：**产出能直接用于复习和自测的卡片，而不是更短的摘要**。每张卡片
只讲一个知识点、可以脱离其他卡片独立阅读（因为复习时顺序会被打乱），并且卡片上的每一条信息都能
在原文里找到出处。

## 二、主要功能

**卡片结构固定为四个字段**

| 字段 | 内容 |
| --- | --- |
| 标题 | 这张卡片要讲的那一个点，写成一句断言 |
| 核心知识 | 需要记住的知识本身，1~2 句，单独拿出来也完整 |
| 简明解释 | 它为什么成立、机制是什么，1~3 句，必须比核心知识多说一点 |
| 例子或自测问题 | 只放一项：原文给的例子，或一个能用原文回答的自测问题 |

**五条硬性约束（决定产出是否合格）**

1. **不编造**：不补充原文没有的事实、数字、例子、结论，也不"顺手修正"原文；某个点离开原文就讲
   不清时，直接放弃这张卡片。
2. **不凑数**：原文只支持 3~4 张就给 3~4 张，并在末尾用一行 `说明：` 讲清原因；绝不为凑数量拆分
   知识点或抬高次要细节。
3. **一张卡片一个知识点**：一张卡片如果塞进两个独立主张，就拆成两张，或丢掉不值得成卡的那个。
4. **不重复**：会被原文同一句话回答的两张卡片，只保留更强的那张。
5. **合并而非拆分**：原文给出"规则"再给出它"必然的推论"，这是同一个知识点；两张卡片若会被彼此
   的核心知识回答，就必须合并（这条规则专门用来防止"靠拆分凑数量"）。

**输入处理**

- 支持粘贴文本，以及本地 `.md` / `.markdown` / `.txt` 文件。
- 文件不是 UTF-8 时回退到本机默认编码（如 Windows 上的 GBK），而不是直接报错——已用 GBK 编码的
  中文操作文档实测通过。
- 原文包含多个不相关主题时，先选定最核心的主题、在输出里写明覆盖范围，并说明其余主题被略过；
  原文超出 8 张卡片容量时先缩小范围，不会把一本书硬压成 8 张。
- 素材连 3 个独立知识点都不够时，用一两行说明太短、列出仅有的内容并请用户补充，而不是产出空洞卡片。

**语言**

字段标签与标题层级固定（便于检索与对比），卡片内容用原文语言书写，并遵循该语言的标点习惯；
技术术语、命令、标识符保持原样。

**明确不做的事**

不抓取网页、不解析 PDF / Word 等二进制文档、不导出 Anki 牌组、不提供图形界面或批量脚本。
只给一个链接而没有正文时，会说明缺少正文并请你粘贴，而不会猜测链接里的内容。

## 三、安装方法

Skill 就是一个目录，复制到你的 Skill 目录即可：

```powershell
# Codex 默认目录
Copy-Item -Recurse .\make-knowledge-cards "$env:USERPROFILE\.codex\skills\"
```

```bash
# 其他兼容 Agent Skills 约定的位置
cp -r make-knowledge-cards ~/.codex/skills/
```

必需文件只有两个：`SKILL.md`（必读）和 `agents/openai.yaml`（界面元数据）。`references/example.md`
只在需要校准卡片粒度时读取，删除它不影响使用。

## 四、使用方法

自动匹配：直接描述任务即可，例如

```text
把下面这篇文章做成知识卡片：
<粘贴文章正文>
```

显式调用：

```text
使用 make-knowledge-cards，把下面这篇文章做成知识卡片：
<粘贴文章正文>
```

```text
使用 make-knowledge-cards 处理 ./notes/某篇文章.md
```

输出默认直接给在回复里；只有你明确要求时才会写成文件。

## 五、输入输出示例

### 示例一：知识点不足的文章（不凑数量）

输入 `test/article-coffee-thin.md`（全文只有 11 行，节选）：

`````markdown
# 咖啡豆冷冻的几点说明

烘焙后的咖啡豆风味流失主要来自与空气接触后的氧化，温度只是影响这个过程快慢的因素之一。

把豆子放进冷冻室能够显著放慢风味流失，这是低温带来的直接结果。需要强调的是，决定冷冻是否
有用的不是冷冻本身，而是分装……

分装成一次用量之后，取出后不需要长时间回温，静置很短的时间就可以研磨。

另外，这条说明只针对已烘焙的咖啡豆。生豆的保存方式完全不同，不在此列。
`````

输出（**4 张卡片**，以下是完整输出）：

````markdown
# 知识卡片：咖啡豆冷冻的几点说明

来源：article-coffee-thin.md · 卡片数：4（覆盖范围：全文）
覆盖要点：烘焙豆风味流失的主因是氧化、温度只决定快慢；决定冷冻效果的是分装而非冷冻本身；分装后不需要长时间回温；适用范围仅限已烘焙豆

---

## 卡片 1：烘焙咖啡豆风味流失的主因是氧化，温度只决定快慢

**核心知识**：烘焙后咖啡豆的风味流失主要来自与空气接触后的氧化，温度只是影响这个过程快慢的因素之一。

**简明解释**：决定流失的是氧化本身，低温能做的只是减慢它，所以冷冻把流失变慢，却没有改变流失的原因。

**例子或自测问题**：烘焙咖啡豆风味流失的主要原因是什么，温度在其中起什么作用？

---

## 卡片 2：决定冷冻是否有效的是分装，而不是冷冻本身

**核心知识**：冷冻能不能有效保住风味，取决于是否分装成一次用量，而不是冷冻这个动作本身。

**简明解释**：如果反复把整袋豆子取出、解冻、再冻回去，每次取出都在让豆子接触空气和湿气，风味下降会很快；分装把这种反复接触压到了最低。

**例子或自测问题**：把整袋豆子反复取出、解冻、再冻回去，风味为什么会下降得很快？

---

## 卡片 3：分装成一次用量后，取出不需要长时间回温

**核心知识**：分装成一次用量之后，豆子从冷冻室取出后不需要长时间回温，静置很短的时间就可以研磨。

**简明解释**：这条做法以"每次取出的量一次用完"为前提，回温只需让豆子达到可研磨的状态，不必像对待整袋豆子那样等待。

**例子或自测问题**：分装成一次用量的冷冻豆子取出后，需要回温很长时间才能研磨吗？

---

## 卡片 4：这套冷冻保存的做法只适用于已烘焙的咖啡豆

**核心知识**：这条说明只针对已烘焙的咖啡豆，生豆的保存方式完全不同，不在此列。

**简明解释**：来源没有给出适用于生豆的结论，只说明两者的保存方式完全不同，所以分装与冷冻的做法不能照搬到生豆上。

**例子或自测问题**：关于冷冻与分装的这套做法，可以照搬到生豆的保存上吗？

---

说明：来源较短，只支持 4 个互相独立的知识点（"冷冻能放慢风味流失"是"氧化致流失、温度只影响速度"的直接结果，按同一单元处理；"反复解冻使风味快速下降"作为"分装决定效果"的后果并入），因此未凑到 5 张。
````

这里最能说明问题的是：这一篇在前两轮测试里都被做成了 5 张，其中"温度只影响快慢"和"所以冷冻能放慢
流失"被拆成了两张卡片——但第二张会被第一张的同一句话回答，按合并规则它们属于同一个知识点。第 5 条
约束就是为这种情况写的；把合并测试写成可逐对执行的检查之后，同一篇原文稳定收敛为上面的 4 张。

### 示例二：英文原文（标签固定，内容随原文语言）

输入 `test/article-pool-english.md`（标题为 *Why a bigger connection pool usually makes things worse*），
输出中的字段标签保持中文以便检索，内容用英文：

`````markdown
# 知识卡片：Why a bigger connection pool usually makes things worse

来源：article-pool-english.md · 卡片数：5

---

## 卡片 1：Raising the pool size moves the queue, it does not shorten it

**核心知识**：A database can only execute a limited number of queries at once, well below the number
of connections a typical application opens, so connections beyond that limit queue inside the
database while still holding their connection.

**简明解释**：The extra connections add no throughput because the execution limit has not changed;
they only relocate the waiting from the application side to inside the database.

**例子或自测问题**：When requests time out, why does raising the pool size tend to produce more
timeouts instead of fewer?
`````

### 边界示例

| 用户请求 | Skill 的行为 |
| --- | --- |
| 只给一个 URL，说"帮我做成卡片" | 说明不支持抓取网页，请你把正文粘过来或给本地文本文件 |
| 粘贴 3 句话，其中只有 1 个知识点 | 说明内容太短、指出仅有的内容，并请你补充；不产出 1~2 张的空洞卡片 |
| "再加几张卡片，用你知道的最佳实践补充" | 拒绝补充原文之外的内容，只按原文出卡片 |
| "导出成 Anki 牌组" | 说明不支持 Anki 导出，但可以给出 Markdown 卡片供你自行导入 |

## 项目结构

```text
.
|-- make-knowledge-cards/        可直接复制到 Skill 目录的成品
|   |-- SKILL.md                 卡片字段、五条硬性约束、六步流程、自检清单、输出格式
|   |-- agents/
|   |   `-- openai.yaml          界面元数据：显示名、简介、默认提示词
|   `-- references/
|       `-- example.md           校准示例：一段短文如何变成一组卡片
|-- test/                        开发期间的测试材料与评估记录（发布时可删除）
|   |-- article-*.*              5 篇不同类型的测试原文（含一个故意用 GBK 编码的文件）
|   `-- evaluation-notes.md      每轮测试的结论与逐条修复记录
|-- LICENSE                      MIT 许可证
`-- README.md
```

## 开发与验证记录

Skill 由 skill-creator 的官方初始化工具创建：

```powershell
python init_skill.py make-knowledge-cards --path <目标目录>
```

结构校验用官方脚本 `quick_validate.py`（Windows 上如遇中文文件报编码错误，加上 UTF-8 模式）：

```powershell
$env:PYTHONUTF8="1"
python quick_validate.py .\make-knowledge-cards
```

开发期间对 4 类内容、5 个文件做了三轮独立前向测试——论点型中文长文、含命令的操作文档（同一篇同时
提供了 UTF-8 与 GBK 两份，用来验证编码回退）、知识点稀薄的短文、英文技术短文。每轮测试都由只拿到
Skill 和原文、不知道检查重点的独立 agent 完成；之后又对成稿做了一轮一致性审计。三轮测试与审计共
修改了 15 处规则，其中最关键的一处是"合并而非拆分"。逐条结论、原文的知识点清单和修复记录见
[test/evaluation-notes.md](test/evaluation-notes.md)。
